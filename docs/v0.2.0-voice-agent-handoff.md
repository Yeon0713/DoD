# v0.2.0 음성 앱과 에이전트 백엔드 인수인계

도나(DONNA) v0.2.0 음성 앱에 **멀티 에이전트 백엔드를 붙이는 사람**을 위한 인수인계 문서입니다.
어떤 기능이 필요한지, 어떤 입력에 어떤 출력이 나와야 하는지, 미리 알고 있어야 하는 데이터가 무엇인지를 적었습니다. 이 문서대로 하네스를 짜면 앱과 연결됩니다.

> 기준: 2026-11-16 (v0.2.1 화면 포맷 반영)
> 화면 기준: Figma `DONNA-UX-UI` › 페이지 `v0.2.1 : 디자인개선` › 묶음 **D · v0.2.1 · 하루 시나리오**(D-01 ~ D-33), **E · v0.2.1 · 시작, 로그인, 마이크 허용**(E-01 ~ E-05), **F · v0.2.1 · 알바생 앱**(F-01 ~ F-09)
> https://www.figma.com/design/wXGnsDy7RlcIWL3cJCcV3Z/DONNA-UX-UI?node-id=500-2
> 화면 번호는 v0.2.1 페이지 번호입니다. v0.2.0 페이지의 D-01 ~ D-12와 번호가 다릅니다 (짝은 17-3). 화면 틀(머리, 가게 상태 줄, 칩 없음, 도나 자리)은 17장에 있습니다.

**전제**

- 지금 저장소에 있는 앱(`mobile/`, `frontend/`)과 그 API(`/api/today`, `/api/plan` 등)는 **쓰지 않습니다.** v0.2.0은 Figma 확정안을 기준으로 새로 만듭니다.
- 이 문서의 API 이름과 JSON 모양은 **새로 정하는 제안**입니다. 아직 구현된 것은 없습니다. 바꾸고 싶은 곳이 있으면 구현 전에 알려 주세요. 14장에 아직 정해지지 않은 것을 모아 두었습니다.
- 구현 범위는 **오늘 일정 브리핑** 하나입니다. 메뉴바의 다른 탭(일정, 매출, 설정)은 Figma 화면이 아직 없습니다.

## 1. 한 장으로 보기

### 무엇을 만드나

사장님은 설거지나 매장 일을 하느라 휴대폰을 만지기 어렵습니다. 그래서 **말로 묻고 말로 듣습니다.** 화면은 못 들었을 때 눈으로 확인하는 곳입니다.

- 앱이 켜져 있으면 버튼 없이 듣고, **"도나야"로 부른 말에만 답합니다** (2026-11-16 결정, 3-4장).
- 도나는 **묻기 전에는 말하지 않습니다.** 밤사이 리뷰가 와도 먼저 알리지 않습니다.
- 도나는 퇴근 뒤부터 출근 전까지 데이터를 모으고, **출근 한 시간 전**부터 그날 브리핑을 준비합니다.
- 사장님이 "오늘 일정 브리핑해 줘"라고 하면 그때 말합니다.

### 누가 무엇을 하나

| 파트 | 하는 일 | 만드는 사람 |
|---|---|---|
| **앱 (음성 클라이언트)** | 마이크로 듣기, 말을 글자로 바꾸기(STT), 서버에 보내기, 받은 답을 화면에 그리기, 소리 내어 읽기(TTS) | 앱 담당 |
| **에이전트 백엔드** | 밤사이 데이터 모으기, 리뷰 나누기와 답글 쓰기, 브리핑 준비하기, 사장님 말의 뜻을 알아듣고 답 만들기 | **이 문서를 받는 사람** |

경계는 하나입니다. **앱은 "사장님이 한 말(글자)"을 보내고, 백엔드는 "도나가 할 말 + 화면에 띄울 카드"를 돌려줍니다.** 이어서 할 말을 보여 주던 칩(추천 답변)은 v0.2.1에서 없앴습니다. 소리(오디오)는 백엔드로 가지 않습니다.

```
[사장님] 말 ─▶ [앱] 마이크 ─▶ STT ─▶ POST /v1/turn (글자)
                                            │
                                   [에이전트 백엔드]
                                   뜻 파악 → 준비해 둔 브리핑에서 답 꺼내기
                                            │
[사장님] 귀·눈 ◀─ TTS + 화면 ◀─ [앱] ◀─ 응답 (말할 문장 + 카드)
```

### 백엔드가 지켜야 할 것 다섯 가지

1. **브리핑은 미리 만들어 둡니다.** 사장님이 물은 뒤에 계산하면 늦습니다. 브리핑 단계는 1초 안에 답해야 합니다 (11장).
2. **화면에 들어갈 글자는 길이 한도가 있습니다.** 한도를 넘으면 화면이 깨집니다 (6장).
3. **말할 문장과 보여 줄 문장은 따로 줍니다.** 말은 길고 자연스럽게, 화면 글은 짧게.
4. **사장님에게 한 말이 아니면 답하지 않습니다.** 부르지 않은 말은 앱이 보내지 않지만, 브리핑 중에는 부르지 않은 말도 들어옵니다 (4장 `ignore`).
5. **인사말이나 앱 설명 문장을 만들지 않습니다.** "말씀만 하세요", "손이 바빠도 제가 듣고 있어요" 같은 문장은 금지입니다. 사장님이 알아야 할 사실만 말합니다 (12장).

## 2. 필요한 기능

백엔드가 해야 하는 일은 **미리 해 두는 일**(F1 ~ F7)과 **사장님이 말할 때 하는 일**(F8 ~ F10)로 나뉩니다.

| 번호 | 기능 | 언제 | 화면 |
|---|---|---|---|
| F1 | 데이터 모으기 | 퇴근 뒤 ~ 출근 전, 계속 | 없음 |
| F2 | 리뷰 나누고 줄이기 | 리뷰가 들어올 때마다 | D-09, D-11 |
| F3 | 아쉬운 리뷰에 바로 답하기 | 아쉬운 리뷰가 들어온 뒤 30분 안 (허락받은 경우만) | D-11 |
| F4 | 고칠 점 찾기 | 브리핑 준비 때 | D-11 |
| F5 | 좋은 리뷰 일주일 분석 | 브리핑 준비 때 | D-12 |
| F6 | 좋은 리뷰 답글 쓰고 올릴 때 정하기 | 브리핑 준비 때 | D-13 |
| F7 | 브리핑 묶음 만들기 | 출근 한 시간 전 | D-07, D-08 ~ D-13, D-16 |
| F8 | 말의 뜻 알아듣기 | 사장님이 말할 때 | 전체 |
| F9 | 답 만들기 | 사장님이 말할 때 | 전체 |
| F10 | 허락 기억하기 | 사장님이 허락하거나 거절할 때 | D-10 |

### 기능별 입력과 출력

| 기능 | 입력 | 출력 | 미리 필요한 데이터 |
|---|---|---|---|
| **F1** 모으기 | 가게 id, 지금 시각 | 그날의 리뷰, 예약, 행사, 경기, 날씨를 저장소에 적재 | 가게 위치, 영업시간 (8장) |
| **F2** 리뷰 나누기 | 리뷰 한 건 (별점, 글) | `sentiment`(좋은/아쉬운), `topic`(배달, 맛, 양, 응대, 위생, 기타), `summary`(한 줄 요약) | 없음 |
| **F3** 바로 답하기 | 아쉬운 리뷰 한 건, 허락 여부 | 답글 글, 올린 시각, 걸린 분, 답글 한 줄 요약 | 허락 설정, 가게 이름, 답글 금지 규칙 (12장) |
| **F4** 고칠 점 | 최근 아쉬운 리뷰들과 `topic` | 고칠 점 한 문장, 근거(언제 몇 건) | 최근 4주 리뷰, 주문 시각 |
| **F5** 일주일 분석 | 최근 7일 좋은 리뷰들 | 좋아한 점 상위 3개(이름, 횟수), 지키는 방법 한 문장 | 메뉴 이름 |
| **F6** 답글 예약 | 답글 안 단 좋은 리뷰들, 이번 주 날씨·행사·경기 | 리뷰마다 답글 글, 올릴 시각, **이유**(종류, 한 줄 설명) | 날씨 예보, 행사, 경기, 메뉴 |
| **F7** 브리핑 묶음 | F1 ~ F6의 결과 | 홈 요약 + 브리핑 5단계의 응답 (4 ~ 5장의 JSON) | 전부 |
| **F8** 뜻 알아듣기 | 사장님이 한 말(글자), 직전 상황 | `intent` 하나 (7장) | 직전 턴, 브리핑 진행 위치 |
| **F9** 답 만들기 | `intent`, 브리핑 묶음 | 응답 JSON (4장) | 브리핑 묶음 |
| **F10** 허락 기억 | 허락 종류, 예 또는 아니오 | 저장된 설정 | 없음 |

**F6의 이유가 이 서비스의 핵심입니다.** 좋은 리뷰 답글은 바로 달지 않고, 가장 잘 보일 때에 맞춰 예약합니다. 사장님께는 "언제, 왜"를 함께 말합니다.

| 이유 종류 (`reason.kind`) | 예 |
|---|---|
| `weather` | 목요일에 비가 와서, 그날 아침에 비 오는 날 전골을 권하는 답글을 올립니다 |
| `game` | 금요일 한국시리즈 전에, 경기 보기 전에 들르시게 올립니다 |
| `event` | 주말 축제 전날에 미리 올려 답글을 보고 방문하게 합니다 |
| `weekend` | 리뷰를 많이 보는 토요일 오전에 모아서 올립니다 |
| `season` | 날이 추워져서 국물 메뉴를 권하는 답글을 올립니다 |

## 3. 음성 입력

### 3-1. 앱이 하는 일과 백엔드가 받는 것

- **STT와 TTS는 앱에서 합니다.** 백엔드는 글자만 주고받습니다. (제안입니다. 14장 1번)
- 앱은 말하는 도중의 글자(중간 결과)를 화면 맨 아래 듣기 알약에 그대로 보여 줍니다(부품 `음성/듣기 알약`의 받아쓰는 중 모양). **중간 결과는 백엔드로 보내지 않습니다.**
- 말이 끝나면 앱이 **최종 글자 한 번**을 `POST /v1/turn`으로 보냅니다.
- v0.2.1부터 화면에 칩(추천 답변)이 없습니다. 사장님은 말로만 답하고, `source`는 늘 `"voice"`입니다.

### 3-2. 앱의 상태

| 상태 | 듣기 알약 | 도나 | 화면 |
|---|---|---|---|
| `listening` 듣는 중 | 듣고 있어요 | 정지 | D-07, D-08, D-10, D-17 |
| `hearing` 받아쓰는 중 | 받아쓴 말 | 타이핑 반복 | 부품 `음성/듣기 알약` |
| `waiting` 답을 기다리는 중 | (Figma에 아직 없음, 14장 5번) | | |
| `speaking` 말하는 중 | 도나가 말하고 있어요 | 타이핑 반복 | D-09, D-12, D-13, D-16, D-29 |
| `not_understood` 못 알아들음 | 한 번 더 말씀해 주세요 | 정지 | D-28 |

**도나 자리 (v0.2.1)**: 듣기 알약 바로 위 가운데, 크기 144 하나입니다. 상태에 따라 정지와 타이핑 반복만 바뀝니다. 대화 영역의 내용이 도나 자리까지 내려오면 앱이 도나를 숨깁니다 (6장).

도나가 말하는 동안에도 마이크는 켜져 있습니다. **사장님이 끼어들면** 앱은 읽기를 멈추고 새 말을 보냅니다. 이때 도나가 어디까지 말했는지를 함께 보냅니다(`context.heard_until`).

### 3-3. 앱이 걸러서 보내지 않는 것

| 경우 | 앱이 하는 일 |
|---|---|
| 글자가 비었거나 2자 미만 | 보내지 않음 |
| STT 신뢰도(`confidence`)가 0.5 미만 | 보내지 않고 D-28(못 알아들음)을 띄움 |
| 도나가 읽는 소리가 마이크로 다시 들어온 것 | 보내지 않음 (앱이 자기 소리를 거름) |

신뢰도 0.5 이상이면 뜻이 이상해 보여도 **그대로 보냅니다.** 뜻을 판단하는 것은 백엔드의 일입니다.

### 3-4. 백엔드가 감안해야 할 것

- **주방은 시끄럽습니다.** 글자가 틀리게 들어옵니다. 예: "오늘 일정 브리핑해 줘" → "오늘 일정 부리핑 해줘", "오늘 일정 브리핑 해 조". 글자가 조금 틀려도 뜻을 알아들어야 합니다.
- **호출어는 "도나야"입니다 (2026-11-16 결정).** 앱이 걸러서, 아래 경우의 말만 백엔드로 보냅니다.
  - "도나야"로 시작한 말: 부르는 말을 떼고 `utterance.addressed: true`로 보냅니다. "도나야"만 부른 뒤 8초 안에 이어진 첫 마디도 `addressed: true`입니다. **이런 말은 `ignore` 하지 않습니다.** 모르는 말이면 `not_understood`입니다.
  - 브리핑 중이거나 도나가 물어본 뒤, 도나가 답한 뒤 8초 안: 부르지 않아도 보냅니다 (`addressed: false`). 여기에는 직원이나 손님에게 한 말이 섞일 수 있으니, 도나에게 한 말이 아니면 `ignore`로 답합니다. 틀리게 답하는 것보다 가만히 있는 편이 낫습니다.
  - 그 밖의 말은 화면에 적지도, 백엔드로 보내지도 않습니다.
  - 받아쓰기가 "돈아야", "또나야"로 적어도 부른 것으로 봅니다. 부르는 말이 붙은 채로 와도 백엔드가 떼고 알아들어야 합니다.
- **숫자와 시각은 말로 들어옵니다.** "일곱 시", "열두 명", "내일모레".
- 말투는 반말과 존댓말이 섞입니다. "브리핑해 줘", "브리핑해 주세요", "브리핑".

## 4. API

기본 주소는 구현하는 쪽이 정합니다. 예시는 `http://localhost:8100`으로 적습니다. 모두 JSON이고 글자는 UTF-8입니다. 시각은 `2026-11-17T09:02:11+09:00`처럼 시간대를 붙인 ISO 8601입니다.

| API | 쓰는 때 | 화면 |
|---|---|---|
| `GET /v1/home` | 앱을 켰을 때, 브리핑이 끝났을 때 | D-07 |
| `POST /v1/turn` | 사장님이 말했을 때, 다음 단계로 저절로 넘어갈 때 | D-08 ~ D-16, D-28, D-29 |
| `GET /v1/settings`, `PATCH /v1/settings` | 허락 확인과 변경 | D-10 |
| `POST /v1/dev/*` | 개발과 시연 (9장) | 없음 |

### 4-1. `GET /v1/home`

앱을 켜면 맨 먼저 부릅니다. **도나가 무엇을 준비해 뒀는지**를 돌려줍니다.

요청: `GET /v1/home?store_id=s001`

응답:

```json
{
  "store": { "id": "s001", "name": "도나네 곱창 역삼점", "logo_url": "https://example.com/logos/s001.png", "open_time": "10:00", "close_time": "22:00" },
  "date": "2026-11-17",
  "date_label": "11월 17일 화요일",
  "store_status": { "state": "before_open", "label": "영업 전", "detail": "오전 10시에 열어요" },
  "briefing_ready": true,
  "prepared_at": "2026-11-17T09:00:00+09:00",
  "headline": "오늘 일정 브리핑 준비했어요",
  "cards": [
    {
      "type": "rows",
      "id": "prepared",
      "rows": [
        { "id": "p_schedule", "kind": "schedule", "value": "행사, 경기, 예약 5팀" },
        { "id": "p_reviews", "kind": "reviews", "value": "밤사이 리뷰 5개 읽어 둠" },
        { "id": "p_replies", "kind": "scheduled_replies", "value": "좋은 리뷰 답글 3개 예약" }
      ]
    }
  ]
}
```

- `store.name`, `store.logo_url`, `date_label`, `store_status`는 **모든 사장님 화면 맨 위 머리와 가게 상태 줄**에 씁니다 (17-1). 앱은 홈을 부를 때 받아 두고, 화면을 켜 둔 채 여는 시각이나 닫는 시각을 지나면 `open_time`, `close_time`으로 상태를 다시 계산합니다.
- `store_status.state`는 세 가지입니다. `before_open`: "영업 전", "오전 10시에 열어요". `open`: "영업 중", "밤 10시에 닫아요". `closed`(닫는 시각 뒤): "영업 끝", "내일 오전 10시에 열어요". `detail`은 폭 14 안 (6장).
- `logo_url`이 없으면 앱이 매장 이름 첫 글자를 둥근 네모에 넣습니다 (제안, 14장 15번).
- 응답에 `suggestions`는 없습니다 (v0.2.1에서 칩을 없앴습니다).
- 홈에서는 도나가 **말하지 않습니다.** `say`가 없습니다.
- 준비한 것이 없는 줄은 뺍니다. 예: 밤사이 리뷰가 없으면 `p_reviews` 줄이 없습니다.
- `briefing_ready`가 `false`인 경우(출근 한 시간 전보다 이른 때)의 화면은 Figma에 아직 없습니다 (14장 6번).

### 4-2. `POST /v1/turn` 요청

```json
{
  "request_id": "req_7f3a2c",
  "store_id": "s001",
  "session_id": "sess_20261117_s001",
  "client_time": "2026-11-17T09:02:11+09:00",
  "utterance": {
    "text": "오늘 일정 브리핑해 줘",
    "confidence": 0.93,
    "source": "voice",
    "addressed": true,
    "started_at": "2026-11-17T09:02:08+09:00",
    "ended_at": "2026-11-17T09:02:10+09:00"
  },
  "event": null,
  "context": {
    "last_turn_id": null,
    "donna_was_speaking": false,
    "heard_until": null
  }
}
```

| 칸 | 뜻 |
|---|---|
| `request_id` | 앱이 만든 고유 번호. 같은 번호로 다시 오면 **같은 응답**을 돌려줍니다 (통신이 끊겨 다시 보낸 경우) |
| `session_id` | 가게와 날짜마다 하나. 브리핑이 어디까지 갔는지를 백엔드가 이 번호로 기억합니다 |
| `utterance` | 사장님이 한 말. `source`는 `"voice"` 하나입니다 (v0.2.1에서 칩을 없애 `"chip"`은 오지 않습니다) |
| `event` | 말이 아닌 신호. 지금은 `"auto_next"` 하나뿐. 이때 `utterance`는 `null` |
| `context.last_turn_id` | 앱이 마지막으로 받은 응답의 `turn_id` |
| `context.donna_was_speaking` | 사장님이 끼어들었으면 `true` |
| `context.heard_until` | 끼어들었을 때 도나가 어디까지 말했는지. `{ "turn_id": "t_0142", "say_index": 1 }` |

**`auto_next`**: 도나가 한 단계를 다 말한 뒤 사장님이 3초 동안 아무 말도 하지 않으면, 앱이 `event: "auto_next"`를 보냅니다. 백엔드는 "다음"과 똑같이 처리합니다. 단, `ask_permission`으로 **물어본 뒤에는 앱이 `auto_next`를 보내지 않습니다.** 대답을 기다립니다.

### 4-3. `POST /v1/turn` 응답

```json
{
  "turn_id": "t_0142",
  "type": "answer",
  "intent": "briefing.start",
  "owner_said": "오늘 일정 브리핑해 줘",
  "briefing": { "step": 1, "total": 5, "step_key": "schedule" },
  "headline": "오늘은 저녁이 바빠요",
  "say": [
    { "text": "오늘은 저녁이 바빠요.", "caption": null, "focus": [] },
    { "text": "강남 페스티벌과 한국시리즈가 있어요.", "caption": null, "focus": ["s_event", "s_game"] },
    { "text": "일반 예약이 네 팀 있어요.", "caption": null, "focus": ["s_resv"] },
    { "text": "저녁 7시에는 단체 손님 열두 분이 오세요.", "caption": null, "focus": ["s_group"] }

    {
      "type": "rows",
      "id": "schedule",
      "rows": [
        { "id": "s_event", "kind": "event", "value": "강남 페스티벌 저녁 6시" },
        { "id": "s_game", "kind": "game", "value": "한국시리즈 저녁 6시 30분" },
        { "id": "s_resv", "kind": "reservation", "value": "저녁 예약 4팀" },
        { "id": "s_group", "kind": "group_reservation", "value": "저녁 7시 단체 12명" }
      ]
    }

}
```

| 칸 | 뜻 | 화면에서 |
|---|---|---|
| `turn_id` | 이 응답의 번호 | 없음 |
| `type` | 응답 종류 (4-4) | |
| `intent` | 백엔드가 알아들은 뜻 (7장). 확인용 | 없음 |
| `owner_said` | 사장님이 한 말을 **다듬은 글자**. STT가 틀린 글자를 바로잡아 줍니다. 말이 아닌 신호(`auto_next`)면 `null` | 오른쪽 색이 찬 말풍선 |
| `briefing` | 브리핑 중이면 지금 단계와 전체 단계. 아니면 `null` | 위쪽 게이지바 |
| `headline` | 도나의 첫마디. **한 줄.** 숫자는 아라비아 숫자 (12장) | 왼쪽 세로 선 옆 큰 글자 |
| `say[]` | 소리 내어 읽을 문장들. 순서대로 읽습니다 | |
| `say[].text` | **읽을 문장.** 자연스러운 말. 숫자는 읽는 대로 ("열두 분") | 없음 (소리만) |
| `say[].caption` | 그 문장을 읽는 동안 **화면에 보일 짧은 문장.** 카드에 없는 것(이유, 되돌리는 법, 질문)일 때만 줍니다. 카드 줄과 같은 내용이면 `null`입니다 (v0.2.1). `null`이면 직전 것을 그대로 둠 | 첫마디 아래 한 줄 |
| `say[].focus` | 그 문장을 읽는 동안 진하게 표시할 줄의 `id`들 | 카드 안의 줄 강조 |
| `cards[]` | 화면에 띄울 카드 (5장). 없으면 `[]` | 가운데 카드 |
| `expects_reply` | 도나가 물어봤고 대답을 기다리면 `true` | 앱이 `auto_next`를 보내지 않음 |

### 4-4. 응답 종류 (`type`)

| `type` | 뜻 | 앱이 하는 일 | 화면 |
|---|---|---|---|
| `answer` | 보통의 답 | `say`를 읽고 카드를 띄움 | D-08, D-09, D-11 ~ D-13, D-29 |
| `ask_permission` | 도나가 허락을 구함. `permission.key`가 함께 옴 | 읽고, 대답을 기다림 | D-10 |
| `ask_action` | 영업 중 아쉬운 리뷰: 사과 답글과 알바생 교정 카드를 올릴지 물음. `action`이 함께 옴 (21장) | 읽고, 8초 동안 "도나야" 없이 대답을 받음 | 아직 Figma 없음 |
| `show_detail` | 자세한 내용을 화면에 띄움 | 짧게 한 마디만 읽고 카드를 띄운 뒤 가만히 있음 | v0.2.1 화면 없음 |
| `end` | 브리핑이 끝남 | 읽고, 듣는 상태로 돌아감 | D-16 |
| `not_understood` | 도나에게 한 말인데 뜻을 모름 | "잘 못 들었어요. 한 번 더 말씀해 주세요."를 읽음. 화면은 그대로 | D-28 |
| `ignore` | 도나에게 한 말이 아님 | **아무것도 하지 않음.** 화면도 소리도 그대로 | 없음 |
| `stop` | "그만" | 읽기를 멈추고 홈(`GET /v1/home`)으로 | D-07 |

`not_understood`, `ignore`, `stop`은 `headline`, `say`, `cards`를 비워서 보냅니다 (`null` 또는 `[]`).

### 4-5. 오류

| 상황 | 응답 | 앱이 하는 일 |
|---|---|---|
| 백엔드가 5초 안에 답하지 못함 | (시간 초과) | "지금은 답하기 어려워요. 조금 뒤에 다시 말씀해 주세요."를 읽음 |

| 브리핑이 아직 준비되지 않음 | `200`, `type: "answer"`, `headline: "아직 준비하고 있어요"` | 그대로 읽음 |
| 그 밖의 오류 | `500 { "error": "internal", "message": "..." }` | 시간 초과와 같음 |

## 5. 카드

카드는 여섯 가지입니다. 백엔드는 **무엇인지(`kind`)만** 알려 주고, 아이콘과 색은 앱이 정합니다. 카드 안 숫자(숫자와 단위)는 앱이 굵은 갈색으로 보여 줍니다. 백엔드는 숫자를 아라비아 숫자로 쓰기만 하면 됩니다.

### 5-1. `rows` 줄 목록

D-07(준비해 둔 것), D-08(오늘 일정), D-10(맡기면 이렇게 해요), D-16(오늘 확인한 것)에 씁니다.

```json
{ "type": "rows", "id": "schedule", "rows": [ { "id": "s_event", "kind": "event", "value": "강남 페스티벌 저녁 6시" } ] }
```

| `kind` | 뜻 | 쓰는 화면 |
|---|---|---|
| `event` | 행사 | D-08 |
| `game` | 경기 | D-08 |
| `reservation` | 일반 예약 | D-08 |
| `group_reservation` | 단체 예약 | D-08 |
| `schedule` | 오늘 일정 (묶어서) | D-07 |
| `reviews` | 리뷰 | D-07 |
| `scheduled_replies` | 예약한 답글 | D-07 |
| `reply` | 답글 달기 | D-10 |
| `briefing` | 브리핑 때 알림 | D-10 |
| `off` | 끌 수 있음 | D-10 |
| `done` | 확인한 것 | D-16 |

**v0.2.1부터 `label`은 쓰지 않습니다.** 줄 앞 아이콘이 종류(`kind`)를 말하고, `value`는 그것만 읽어도 뜻이 통하게 씁니다. 예: "받는 사람 / 오늘 나온 사람 모두" → "오늘 나온 사람 모두", "오늘 하지 않기 / 주문 받기" → "주문 받지 않기" (이름표 없이 거꾸로 읽히면 안 됩니다). 줄은 **최대 4개**입니다.

### 5-2. `counts` 두 칸 숫자

D-09(답글 기다리는 리뷰)에 씁니다.

```json
{ "type": "counts", "id": "review_counts", "items": [
  { "id": "c_pos", "kind": "positive", "label": "좋은 리뷰", "count": 3, "unit": "개" },
  { "id": "c_neg", "kind": "negative", "label": "아쉬운 리뷰", "count": 2, "unit": "개" }
] }
```

칸은 **정확히 2개**입니다.

### 5-3. `review` 리뷰

D-11(아쉬운 리뷰에 단 답글), 화면으로 보기(전체, v0.2.1 화면 없음)에 씁니다.

```json
{ "type": "review", "id": "rv_0412", "variant": "summary",
  "rating": 1,
  "text": "배달이 늦어 음식이 식었대요",
  "written_at": "2026-11-16T21:40:00+09:00",
  "reply": { "text": "사과하고, 다음엔 더 빨리 보낸다고 답했어요", "posted_at": "2026-11-16T21:52:00+09:00", "by": "donna" } }
```

| `variant` | `text` | `reply.text` |
|---|---|---|
| `summary` | 리뷰를 한 줄로 줄인 말 | 답글을 한 줄로 줄인 말 |
| `full` | 리뷰 원문 | 올린 답글 원문 |

`reply`는 답글이 없으면 `null`입니다. `reply.by`는 `"donna"` 또는 `"owner"`입니다.

### 5-4. `tip` 한마디

D-12(이렇게 지켜 보세요)에 씁니다. 고칠 점(`improve`)은 v0.2.1 화면에서 뺐습니다 (17-4).

```json
{ "type": "tip", "id": "tip_delivery", "kind": "improve", "text": "금요일 저녁엔 배달 시간을 10분 넉넉히 안내해 보세요" }
```

`kind`는 `"improve"`(고칠 점) 또는 `"keep"`(지킬 점)입니다. 작은 제목("이렇게 고쳐 보세요", "이렇게 지켜 보세요")은 앱이 붙입니다.

막대 길이는 앱이 가장 큰 `count`를 기준으로 그립니다. 막대 오른쪽에는 앱이 "리뷰 9개"처럼 그 점을 말한 리뷰 수를 적습니다. 줄은 **최대 3개**, 많은 순서입니다.

## 6. 글자 길이 한도

화면 너비가 375이고 글자가 큽니다(멀리서도 읽혀야 해서). **한도를 넘으면 줄이 넘어가 화면이 깨집니다.**

길이는 글자 수가 아니라 **폭**으로 셉니다. 한글은 넓고 숫자와 공백은 좁기 때문입니다.

- 한글 한 글자 = **1**
- 숫자, 공백, 문장 부호, 영문 한 글자 = **0.5**

예: "7시에 단체 손님 열두 분이 오세요." → 한글 13자(13) + 숫자 1, 공백 5, 마침표 1(3.5) = **16.5**

| 칸 | 폭 한도 | 화면에 있는 예 (폭) |
|---|---|---|
| `headline` | **15, 한 줄** | 오늘 일정 브리핑 준비했어요 (13.5) |
| `say[].caption` | **18, 한 줄** | 내일은 원래대로 돌아가요. (12.5) |
| `owner_said` | 18이면 한 줄. 넘으면 두 줄까지 (36) | 오늘 일정 브리핑해 줘 (10.5) |
| `store_status.detail` | 14 | 내일 오전 10시에 열어요 (11.5) |
| `rows[].value` | 14 | 한국시리즈 저녁 6시 30분 (12) |
| `counts[].label` | 8 | 아쉬운 리뷰 (5.5) |
| `review.text` (`summary`) | 17, 한 줄 | 배달이 늦어 음식이 식었대요 (13.5) |
| `review.reply.text` (`summary`) | 32, 두 줄 | 사과하고, 다음엔 더 빨리 보낸다고 답했어요 (21) |
| `review.text`, `review.reply.text` (`full`) | 원문 그대로. 길면 화면을 내려서 봄 | |
| `tip.text` | 34, 두 줄 | 금요일 저녁엔 배달 시간을 10분 넉넉히 안내해 보세요 (25.5) |
| `bars[].label` | 12 | 곱창전골 국물 (6.5) |
| `scheduled[].text` | 13 | 경기 보기 전에 들르시게 (11.5) |
| `scheduled[].reason.label` | 8 | 한국시리즈 (5) |
| `scheduled[].time_label` | 6 | 오전 10시 반 (6) |
| `scheduled[].day_label` | 1 | 목 |
| `say[].text` | 한도 없음. **한 문장씩** | |

**한 화면에 들어가는 양 (v0.2.1)**: 화면 위에 머리(65)와 가게 상태 줄(58)이 있고, 대화 영역의 높이는 **486**입니다. 그 안에 게이지바, 사장님 말 풍선, 도나의 말, 카드가 들어갑니다(칩은 없습니다). 게이지바와 말 풍선, 한 줄 제목까지 121을 쓰므로 카드에 쓸 수 있는 높이는 대략 **365**, `caption`이 있으면 **333**입니다. 아래 중 하나까지만 보내세요.

- `rows` 4줄 하나
- `review`(`summary`) 하나 + `tip` 하나
- `bars` 3줄 + `tip` 하나
- `scheduled` 3줄
- `counts` 하나

**도나가 보이는 양**: 도나는 듣기 알약 바로 위에 섭니다. 대화 내용이 위에서 348 안에 끝나야 도나가 보이고, 넘으면 앱이 도나를 숨깁니다. 게이지바, 말 풍선, 제목이 있는 화면이라면 카드가 **227 이하**(`rows` 3줄)일 때 도나가 보입니다. 백엔드가 이 높이에 맞출 필요는 없습니다. 앱이 정합니다.

## 7. 알아들어야 하는 말 (`intent`)

| `intent` | 사장님이 하는 말 (예) | 백엔드가 하는 일 | 응답 |
|---|---|---|---|
| `briefing.start` | 오늘 일정 브리핑해 줘, 브리핑, 오늘 뭐 있어 | 1단계부터 시작 | `answer` (1단계) |
| `briefing.next` | 다음, 넘어가, 계속 (또는 `auto_next`) | 다음 단계로 | `answer`, 마지막이면 `end` |
| `briefing.repeat` | 다시 말해 줘, 뭐라고, 못 들었어 | 지금 단계를 처음부터 다시 | `answer`, `headline`은 "다시 말씀드릴게요" |
| `briefing.restart` | 처음부터 다시 | 1단계로 | `answer` (1단계) |
| `briefing.jump` | 리뷰 어때, 리뷰 보여 줘, 예약 답글은 | 그 단계로 건너뜀 | `answer` (해당 단계) |
| `detail.show` | 화면에 보여 줘, 자세히 보여 줘 | 지금 단계의 자세한 내용 | `show_detail` |
| `detail.read` | 읽어 줘 | 화면에 띄운 내용을 소리 내어 읽음 | `answer` |
| `detail.back` | 돌아가기, 됐어 | 브리핑하던 단계로 돌아감 | `answer` (같은 단계) |
| `permission.yes` | 응 그렇게 해, 그래, 좋아 | 허락을 저장하고 다음 단계로 | `answer` |
| `permission.no` | 아니 내가 볼게, 아니, 됐어 | 거절을 저장하고 다음 단계로 | `answer` |
| `stop` | 그만, 됐어 그만해 | 멈춤 | `stop` |
| `question` | 내일 예약 있어? 이번 주 비 와? | (v0.2.0 범위 밖) 아는 범위에서 답하거나 모른다고 답함 | `answer` |
| `unknown` | 뜻을 알 수 없는 말 | | `not_understood` |
| `not_for_donna` | 3번 테이블 치워 줘, 어서 오세요 | | `ignore` |

**같은 말이 상황에 따라 다른 뜻이 됩니다.** "됐어"는 자세한 화면에서는 `detail.back`, 허락을 물은 직후에는 `permission.no`입니다. `context.last_turn_id`로 직전 응답의 `type`을 보고 판단합니다.

**`ignore`와 `not_understood`를 가르는 기준**: `utterance.addressed`가 `true`("도나야"로 부름)이면 `ignore`는 없고, 모르는 말은 `not_understood`입니다. `false`이면 브리핑, 리뷰, 예약, 일정, 답글, 도나와 관련된 말은 `not_understood`, 가게 운영 중에 사람에게 하는 말로 보이면 `ignore`, 애매하면 `ignore`입니다.

## 9. 목업과 개발용 API

실제 리뷰 플랫폼과 예약 시스템에는 연결하지 않습니다. 대신 개발자 대시보드에서 아래 API로 데이터를 넣고 시각을 움직입니다.

| API | 하는 일 |
|---|---|
| `POST /v1/dev/reviews` | 리뷰 한 건을 넣음 (좋은 리뷰든 아쉬운 리뷰든) |
| `POST /v1/dev/fixtures` | 가게, 예약, 행사, 경기, 날씨를 한꺼번에 넣음 |
| `POST /v1/dev/clock` | 백엔드가 아는 "지금 시각"을 바꿈 |
| `POST /v1/dev/run` | 미리 해 두는 일을 지금 실행 |
| `POST /v1/dev/reset` | 넣은 데이터와 대화 기록을 모두 지움 |
| `GET /v1/dev/state` | 지금 저장된 것을 그대로 보여 줌 (확인용) |
| `POST /v1/dev/demo_review` | 픽스처의 시연 리뷰(`leak`, `missing`, `cold`, `hall`)를 지금 시각에 넣음 (21장) |
| `GET /v1/dev/platform` | 손님 리뷰와 올라간 답글. 시연 화면(`/demo`) 가운데 칸 (21장) |

### `POST /v1/dev/reviews`

```json
{ "store_id": "s001", "platform": "baemin", "rating": 1,
  "text": "배달이 너무 늦어서 다 식어서 왔어요. 곱창은 맛있는데 아쉽네요.",
  "written_at": "2026-11-16T22:40:00+09:00", "order_channel": "delivery" }
```

응답: `{ "review_id": "rv_0412" }`

**문 닫은 뒤에 들어온 리뷰는 앱에 아무것도 보내지 않습니다.** 백엔드만 알고 있다가(나누기, 허락받았으면 바로 답하기), 사장님이 브리핑을 물을 때 말합니다. 영업 중(문 열기 한 시간 전 ~ 문 닫을 때)에 들어온 아쉬운 리뷰는 21장대로 바로 알립니다 (2026-11-18). `written_at`을 비우면 백엔드의 지금 시각, `menus`(주문한 메뉴)를 줄 수 있습니다.

### `POST /v1/dev/clock`

```json
{ "now": "2026-11-17T09:00:00+09:00" }
```

백엔드는 **실제 시계 대신 이 시각**을 써야 합니다. 그래야 "밤에 리뷰가 옴 → 12분 뒤 답글 → 아침 9시 브리핑 준비 → 9시 2분에 사장님이 물음"을 몇 초 만에 돌려 볼 수 있습니다. 시각을 앞으로 옮기면 그 사이에 했어야 할 일(바로 답하기, 예약한 답글 올리기)을 실행합니다.

시계는 서버에 하나입니다. 시계를 멈춰 둔 동안에는 **fixtures 로 넣은 가게(가게 문서 `fixture: true`)의 작업만** 돕니다. 같은 서버에 앱 가입으로 들어온 실제 가게가 있어도 가짜 시각으로 그 가게 리뷰에 답글을 쓰지 않습니다. 실제 가게 작업은 시계를 비워(`{"now": null}`) 실제 시각으로 돌아왔을 때 돕니다 (2026-11-21, 전에는 시계를 15:40으로 옮기면 실제 가게 리뷰 10개 답글까지 써서 5분 넘게 걸렸습니다).

### `POST /v1/dev/run`

```json
{ "store_id": "s001", "job": "prepare_briefing" }
```

`job`: `collect`(F1), `label_reviews`(F2), `auto_reply`(F3), `prepare_briefing`(F4 ~ F7), `post_scheduled`(예약한 답글 올리기)

### 답글을 "올린다"는 것

v0.2.0에서는 실제 플랫폼에 올리지 않습니다. `reply_status`를 `posted`로 바꾸고 `reply_posted_at`을 적는 것이 "올린 것"입니다.

## 10. 브리핑 순서와 화면

브리핑은 **5단계**입니다. `briefing.step`이 게이지바의 칸 수입니다.

| 단계 | `step_key` | 내용 | 화면 | 건너뛰는 때 |
|---|---|---|---|---|
| 1 | `schedule` | 오늘 일정: 행사, 경기, 일반 예약, 단체 예약 | D-08 | 건너뛰지 않음. 아무것도 없으면 "오늘은 평소와 같아요" |
| 2 | `reviews` | 답글 기다리는 리뷰 수, 좋은 리뷰와 아쉬운 리뷰 | D-09 | 답글 기다리는 리뷰가 0개 |
| 3 | `negative` | 아쉬운 리뷰: 허락 묻기, 또는 바로 답한 것과 고칠 점 | D-10 또는 D-11 | 아쉬운 리뷰가 0개 |
| 4 | `positive` | 좋은 리뷰 일주일 분석: 좋아한 점, 지키는 방법 | D-12 | 최근 7일 좋은 리뷰가 3개 미만 |
| 5 | `scheduling` | 좋은 리뷰 답글 예약과 이유 | D-13 | 예약한 답글이 0개 |
| 끝 | | 브리핑 끝 | D-16 | |

건너뛴 단계가 있어도 `briefing.total`은 5 그대로이고, `step`은 건너뛴 만큼 뛰어넘습니다 (게이지바가 한꺼번에 두 칸 찹니다).

### 3단계의 갈림

| `negative_review_auto_reply` | 3단계 응답 |
|---|---|
| `null` (아직 안 물음) | `ask_permission` (D-10). 대답을 받은 뒤 4단계로 |
| `true`, 지난 브리핑 뒤에 바로 답한 리뷰가 있음 | `answer` (D-11): 어떤 리뷰에 몇 분 만에 어떻게 답했는지 + 고칠 점 |
| `true`, 바로 답한 리뷰가 없음 | 건너뜀 |
| `false` | 화면이 아직 없음 (14장 7번) |

| 화면 | 부르는 것 | `type` | `headline` | 카드 |
|---|---|---|---|---|
| D-07 홈 | `GET /v1/home` | | 오늘 일정 브리핑 준비했어요 | `rows` |
| (받아쓰는 중) | (앱 안에서만, 듣기 알약) | | | |
| D-08 오늘 일정 | `turn` `briefing.start` | `answer` | 오늘은 저녁이 바빠요 | `rows` |

## 11. 시각과 속도

### 하루의 흐름

| 때 | 백엔드가 하는 일 |
|---|---|
| 퇴근 (`close_time`) ~ 출근 (`open_time`) | F1 모으기, F2 리뷰 나누기 |
| 아쉬운 리뷰가 들어온 뒤 **30분 안** | F3 바로 답하기 (허락받은 경우만). 영업 중에도 똑같이 합니다 |
| **출근 한 시간 전** (`open_time` - 60분) | F4 ~ F7 브리핑 준비. 끝나면 `GET /v1/home`의 `briefing_ready`가 `true` |
| 출근 뒤 | 사장님이 물으면 답함 (F8 ~ F10) |
| 예약한 시각 | 좋은 리뷰 답글을 올림 |

브리핑을 준비한 뒤에 새 리뷰가 들어오면 **브리핑 묶음을 다시 만듭니다.** 사장님이 오후에 물어도 그때까지의 내용이 나와야 합니다.

### 답하는 속도

말로 하는 대화는 늦으면 못 씁니다.

| 요청 | 목표 |
|---|---|
| `GET /v1/home` | 0.5초 안 |
| `POST /v1/turn` 브리핑 단계 (`start`, `next`, `repeat`, `jump`, `detail.*`) | **1초 안** (미리 만들어 둔 것을 꺼내기만) |
| `POST /v1/turn` 그 밖 (`question`) | 3초 안 |
| 앱의 시간 초과 | 5초 |

**브리핑 단계에서는 LLM을 부르지 않는 것을 권합니다.** 문장과 카드는 F7에서 미리 만들어 두고, 말할 때는 뜻 파악(F8)만 합니다. 뜻 파악도 흔한 말("다음", "다시 말해 줘")은 규칙으로 먼저 걸러서 LLM 없이 답하는 편이 빠릅니다.

## 12. 문장 규칙

### 말투

- 해요체로 씁니다. "~해요", "~했어요", "~할게요".
- 도나는 자기를 "제가"라고 합니다. 사장님을 부를 때는 "사장님".
- 한 문장에 한 가지 사실만 담습니다.
- 숫자는 `say[].text`에서는 읽는 대로("열두 분", "세 개"), 화면 글(`headline`, `caption`, 카드)에서는 **아라비아 숫자**로 씁니다 ("12명", "3개"). 화면에서는 "열두 분" 대신 "12명"입니다 ("12분"은 시간으로 읽힙니다).

### 쓰는 말과 쓰지 않는 말

| 쓰는 말 | 쓰지 않는 말 |
|---|---|
| 오늘 일정 브리핑 | 아침 브리핑, 모닝 브리핑 |
| 좋은 리뷰, 아쉬운 리뷰 | 긍정 리뷰, 부정 리뷰, 악성 리뷰 |
| 답글 | 리플, 댓글, 응대 |
| 확인하기, 먼저 봐 주세요 | 할 일, 지금 하기, 남은 일 |

### 화면 글 (v0.2.1)

- 가운데점(·)으로 잇지 않습니다. "하린 · 오후 6시 32분" → "하린 씨가 오후 6시 32분에 함".
- 카드에 있는 내용을 `caption`으로 다시 쓰지 않습니다. 답 카드에는 제목(`headline`)이 이미 말한 줄을 다시 넣지 않습니다. 단, 기록 카드(보낼 것, 적을 것)와 브리핑 목록(지금 읽는 줄 강조)은 빠짐없이 둡니다.
- 줄 글(`rows[].value`)은 이름표 없이 혼자 읽혀야 합니다 (5-1).

## 16. 목업을 만들면서 더한 것

이 문서의 계약대로 **백엔드 목업과 앱을 실제로 만들었습니다** (`donna-voice/`, 앱 8090, 백엔드 8100). 에이전트를 붙일 때는 `donna-voice/server/`를 바꿔 끼우면 됩니다. 만들면서 계약에 없던 것이 세 가지 생겼습니다.

### 16-1. 응답 종류 `navigate`

"매출 어때", "이번 주 보여 줘"처럼 **다른 탭을 여는 말**입니다. 손을 못 쓰는 사장님이 말로 탭을 옮길 수 있어야 해서 더했습니다.

```json
{ "turn_id": "t_0150", "type": "navigate", "intent": "navigate.sales", "owner_said": "매출 보여 줘",
  "tab": "sales", "say": [ { "text": "어제 128만 원 팔았어요. 지난주 월요일보다 14만 원 많아요.", "caption": null, "focus": [] } ],
  "briefing": null, "headline": null, "cards": [], "expects_reply": false }
```

`tab`은 `home`, `week`, `sales`, `settings` 가운데 하나입니다. 앱은 그 탭으로 옮기고 `say`를 읽습니다. "홈"이라고 하면 `stop`과 같이 처리합니다.

| `intent` | 사장님이 하는 말 (예) |
|---|---|
| `navigate.sales` | 매출 어때, 매출 보여 줘, 얼마 팔았어 |
| `navigate.week` | 이번 주 보여 줘, 언제 바빠 |
| `navigate.settings` | 설정 보여 줘 |

### 16-2. 탭 데이터

| API | 쓰는 곳 | 주요 칸 |
|---|---|---|
| `GET /v1/week` | 일정 탭 (달력) | `days[]` 달력 6주 42일, `week_dates[]` 이번 주 7일, `say`, `scheduled[]` 앞으로 올릴 답글 전부, `past[]` 지난 일 묶음. 하루(`days[]`)의 칸: `in_month`, `is_today`, `is_past`, `marks[]`(`plan` 일이 잡힌 날·`reply` 답글 올리는 날), `title`(큰 한마디: "경기가 있어요". 휴대폰에서 한 줄이 되게 한글 10자 안팎), `weather`, `plans[]` 그날 잡힌 일(`kind`는 `event`·`game`·`group_reservation`·`weather`, `label`, `text`, `short` 태블릿 달력 칸에 적을 짧은 이름: "단체 12명", "한국시리즈", 한글 다섯 자 안팎, `starts_at` 하루 종일이면 `null`, `time_label`. 지난 날에도 준다), `tip` 준비할 것 한 줄(이유를 함께 적는다), `scheduled[]` 그날 올릴 답글, `done[]` 그날 한 것(`actor`는 `donna`·`owner`, `text`, `time_label`), `remaining[]` 오늘 남은 것(`kind`, `text`, `time_label`). **붐빔 예상(바쁨·보통)은 화면에 쓰지 않는다**: 일정 탭은 추측 대신 날짜와 시각이 있는 사실만 보여 준다 |
| `GET /v1/sales` | 매출 탭 | `headline`, `primary` (어제 또는 오늘 지금까지와 지난주 같은 요일), `week.bars[]`, `week.total_label`, `top_menus`. v0.2.1에서 더한 칸은 19장 |

`plans[]`는 모든 날에 채워집니다. 지난 날에는 그 밖에 `done[]`이, 오늘에는 `done[]`, `remaining[]`, `tip`이, 앞날에는 `tip`과 `scheduled[]`가 채워집니다.

**사장님이 한 일을 적는 것**: 브리핑을 끝까지 들으면(`end`) "오늘 일정 브리핑을 들었어요", 허락하거나 거절하면 그 내용을 오늘의 `done[]`에 `actor: "owner"`로 더합니다. 에이전트 백엔드도 이 기록을 남겨야 이번 주 탭이 채워집니다.

**듣는 곳**: 앱은 홈에서만 듣습니다. 이번 주, 매출, 설정 탭에서는 `POST /v1/turn`이 오지 않습니다.

모양은 `donna-voice/server/app/main.py`의 `get_week`, `get_sales`가 기준입니다. 이 두 탭은 Figma에 화면이 없어 새로 정한 것이라, 화면이 확정되면 바뀔 수 있습니다.

### 16-3. `GET /v1/settings`에 더한 칸

`store`, `open_time_label`, `close_time_label`, `briefing_time_label`, `platforms[]`(`key`, `name`, `connected`). v0.2.1에서 브리핑 알림과 장사 시간을 바꿀 수 있게 되었습니다 (19장).

### 19-2. 설정 (`GET`·`PATCH /v1/settings`)

| 칸 | 화면 | 모양 |
|---|---|---|
| `briefing_notify` | 설정 줄 "브리핑 알림", G-08 | `on`, `time`("09:30"), `time_label`("오전 9시 30분"), `is_default`, `default_time`, `options[]`(`time`, `label`, `sub` "문 열기 1시간 전", `is_default`). 고르는 칸은 평소 여는 시각의 2시간 · 1시간 30분 · 1시간 · 30분 전 |
| `hours` | 설정 줄 "장사 시간", G-06 | `summary_label`("10:30 ~ 20:30" 또는 "요일마다 달라요"), `days[]`(월요일부터 `weekday`, `label`, `closed`, `open`, `close`), `naver_days[]`(네이버에서 받은 시간, 다시 불러오기) |

`PATCH`는 보낸 칸만 바꿉니다: `negative_review_auto_reply`(`null`은 "아직 묻지 않음"), `briefing_notify`{`on`, `time`(`null`이면 기본 1시간 전으로)}, `hours`{`days`: 월요일부터 7칸 {`closed`, `open`, `close`}}. 닫는 시간이 여는 시간보다 이르면 400 `bad_hours`.

### 21-1. 흐름 (`server/voice/jobs/review_loop.py`)

## 22. 비 오는 날 스토리 이벤트 → 알바생 할 일 (2026-11-18, 개선안 [2]-3 A3)

고리 [2](온라인 → 오프라인)의 가장 작은 모양입니다. 코드는 `server/voice/instagram/story_event.py`, 시험은 [test-scenarios-closed-loop.md](../donna-voice/docs/test-scenarios-closed-loop.md) I장. **앱(`donna-voice/app`)은 고치지 않았습니다.** 지금 앱이 아는 응답 모양만 씁니다.

상태 (저장소 종류 `story_event`, id `se_<가게>_<날짜>`): `generating → ready → approved → published | card_pinned`, 갈래 `declined`, `failed`.

## 23. 에이전트 조직 개편: 부서·팀장·제안 (2026-11-20)

계획과 결정은 [agent-org-plan.md](../donna-voice/docs/agent-org-plan.md). 도나를 세 부서(고객 응대, 마케팅, 매장 품질 관리)로 나누고, 사원 에이전트는 **제안만** 하며, 팀장 LLM이 판단하고, 도나가 묶어 보고하고, 사장님이 말로 승인하면 코드가 실행합니다.

### 23-1. 사원과 팀장

| 부서 | 사원 (파일) | 무엇을 내나 | 실패하면 |
|---|---|---|---|
| 고객 응대 | 부정 리뷰 (`voice/agents/fix_card.py`) | 교정 할 일(제목·한 문장), 조치 가능 여부, 리뷰 인용 | 원인별 템플릿 (`jobs/cause.py`). 배달 지연은 카드 없음 |
| 고객 응대 | 재방문 유도 (`jobs/schedule.py` + `voice_reply`) | 좋은 리뷰 예약 답글 (바뀌지 않음) | 템플릿 |
| 품질 관리 | 현장 변수 (`voice/agents/field_tasks.py`) | 오늘 날씨·예약 메모에서 할 일 (최대 3) | 제안 없음 |
| 품질 관리 | 매뉴얼 코칭 (`proposals.promote_repeats` + `agents/manual_line.py`) | 7일 안 3번 나온 할 일 → 매일 할 일 제안 | 첫 할 일 제목 그대로 |
| 마케팅 | 소재 발굴 (`agents/topic_finder.py`) | 메뉴 1~3개 + 이야기 한 줄 | 이번 달 많이 나간 메뉴 3개 |
| 마케팅 | 캡션 작성 (`agents/caption_writer.py`) | 글 + 해시태그 8개 이하 (가게 정보 줄은 코드가 붙임) | 템플릿 글 |
| 세 부서 | 팀장 (`agents/team_lead.py`) | 결과마다 keep/drop, 순서, 한 줄 요약. 글은 고치지 않음 | 모두 keep |

켜고 끄기: `VOICE_AGENT_<이름>=false` (`FIXCARD`, `FIELD`, `SAME`, `MANUAL`, `LEAD`, `TOPIC`, `CAPTION`, `HOLIDAY`). 셸 환경 변수 또는 `server/.env`에 적습니다(셸이 먼저). CLOVA 키가 없으면 모두 꺼집니다. 예전부터 있던 `REPLY`, `INTENT`, `IMPROVE`도 같은 방식입니다.

> 2026-11-21 전에는 `server/.env`에 적어도 꺼지지 않았습니다(`.env`가 pydantic Settings 칸으로만 읽혀 `os.environ`에 들어가지 않음). 지금은 `voice/config.py`의 `env()`가 셸 다음 `server/.env`를 봅니다. `VOICE_ALERT_AGENT_REPLY`, `VOICE_DEMO_*`, `VOICE_PREPARED_SNAPSHOT`도 같습니다.

### 23-2. 저장 (voice.db `docs`, 표를 더하지 않음)

- `proposal` (id `pr_<번호>`): `{id, store_id, dept, by, payload{title, detail, phase, repeat, days, must_confirm, urgent, today_impact?}, reason, link, state, same_as, merged, ask_on, lead{verdict, reason, rank, source}, task_id, ...}`
  - 상태 `proposed → asked → applied | declined | expired`, 묶이면 `merged`, 팀장이 빼면 `dropped`
  - 실제로 넣는 곳은 `proposals.apply` 하나 (`staff.add_task`, `origin`·`source` 기록)
- `dept_report` (id `<가게>:<날짜>:<부서>`): `{dept, date, items, verdicts, order, summary, source}`
- `marketing_plan` (id `<가게>:<날짜>`): `{menu_ids, angle, body, hashtags, sources, lead}`
- `field_run`, `holiday_run`: 그날 사원을 돌렸다는 표시
- 가게 문서 `holidays`: `[{date, source: owner | naver, note, confirmed}]`. `hours.on` 이 확정한 날을 쉬는 날로 봅니다

알바생 할 일 표(`staff_tasks`)의 `origin`: `manual | owner | review | story_event | field_variable` (넣는 쪽이 꼭 밝힘. 없으면 오류).

### 23-3. 긴급과 확인 필요

| 할 일 | urgent | must_confirm | 화면 | 퇴근 |
|---|---|---|---|---|
| 리뷰 교정 | 아님 | 예 | 영업 중 묶음의 확인 필요(`groups[].must`, detail 보임). 이틀 | 막지 않음 |
| 비 오는 날 이벤트 | 예 | 예 | 맨 위 붉은 카드(`urgent`) | 막음 |
| 현장 변수 | `today_impact` 이고 팀장이 keep 이면 예 | 예 | 그에 따라 | 그에 따라 |

### 23-4. 응답과 알림 (앱 타입 `donna-voice/app/src/lib/api.ts`)

- `type: "ask_tasks"`: 알바생 할 일 묶어 묻기. 브리핑 마지막 단계 `staff_tasks`(게이지 5). `expects_reply: true`. 카드 `checklist`(id `staff_tasks`, 번호 붙은 항목). 대답: "응, 넣어" / "두 번째는 빼" / "첫 번째는 빼고 넣어" / "안 해"
- `type: "ask_holiday"`: 쉬는 날 확인 ("○월 ○일 ○요일을 쉬는 날로 적을게요. 맞아요?"). 브리핑 단계 `holiday`(일정 뒤, 게이지 1, 네이버에서 읽은 날)
- `action.kind: "review_fix_task"`: 바로 답하기를 켠 가게에서 답글은 올렸고 할 일만 묻는 `ask_action`
- 알림 `negative_auto`: 바로 답하기를 켠 가게의 영업 중 자동 답글 (카드가 있으면 `opens_turn`)
- 새 뜻: `store.holiday`, `store.holiday_cancel`, `holiday.yes`, `holiday.no`

### 23-5. 영업 중 아쉬운 리뷰

| 설정 `negative_review_auto_reply` | 동작 |
|---|---|
| `None` / `False` | 지금처럼 알림 → 묻기. 15분 다시 알림, 25분이면 초안으로 남김(리마인드 문구도 "초안으로 남겨 둘게요") |
| `True` | 묻지 않고 사과 답글을 올림(보상 문장 없음, 카드와 같은 조치). `negative_auto` 알림 → 할 일만 묻기. 25분 대답 없으면 `review_fix_carry` 작업이 다음 날 아침 브리핑으로 넘김 |

실시간 길도 고객 응대 팀장을 짧은 예산(15초, strict)으로 거칩니다.
