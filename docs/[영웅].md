# &#91;영웅\]: 프론트엔드와 UX/UI

&#91;영웅\]이 1차에 만드는 것과 순서다. 이름, 계약, 정답은 공통 탭을 따른다. 작업 카드의 체크를 누르면 진행 상황이 된다.

## 한눈에

- **만드는 것**: 오늘의 카드, 이번 주 달력, 설정, 개발용 시뮬레이터. 디자인 시스템과 알림 문구.
- **기술**: Next.js(App Router) 모바일 웹, PWA. API 호출은 `frontend/lib/api.ts` 한 곳에서만 한다.
- **받는 것**: 1일차 C3 고정 샘플(`contracts/fixtures/`), 2일차 \[여헌\]의 고정 응답 서버(P1), 6일차 끝 API v1(S3)
- **넘기는 것**: 1일차 화면에 필요한 값 목록(\[여헌\]에게), 3일차 화면 시안(팀 리뷰), 9일차 데모 주간 화면 대조 결과
- **기다리는 지점**: S3 하나. 그 전까지는 고정 샘플로 만든다.

## 일정

- **1일차**: K1 계약 확정
- **2일차**: F1 사용자 흐름과 와이어프레임
- **3일차**: F2 디자인 시스템과 화면 디자인
- **4\~5일차**: F3 이번 주 달력
- **5\~6일차**: F4 오늘의 카드와 설정, F5 시뮬레이터
- **7일차**: F6 실제 API 연결
- **8\~10일차**: T1 통합 점검, T2 데모 주간 돌리기, T3 2차 설계

## 작업 카드

### K1 계약 확정 (1일차, 모두)

- [ ] 화면 목록과 화면마다 필요한 값을 적어 \[여헌\]에게 넘긴다.
- [ ] C3 고정 샘플에 데모 주간 화요일 하루가 그대로 들어갔는지 확인한다.

완료 기준: `openapi.yaml`의 예시 응답만으로 네 화면을 그릴 수 있다.

### F1 사용자 흐름과 와이어프레임 (2일차)

- [ ] 알림에서 오늘의 카드로, 필요할 때만 달력으로 가는 흐름. 출근 후, 오후 2시, 마감 전 세 번의 하루를 그린다.
- [ ] 카드 종류별 정보 구조: ① 네 분류, ②, ③, ④, 실행 알림, 월요일 예고, 매출 이상 알림
- [ ] 빠른 응대와 위험 신호 카드에서 근거 리뷰를 펼치는 방식. 리뷰 화면은 따로 두지 않는다(아키텍처 2절).
- [ ] 설정과 시뮬레이터 흐름

완료 기준: 팀 리뷰에서 와이어프레임의 모든 칸을 C3 값으로 채울 수 있다고 확인한다.

### F2 디자인 시스템과 화면 디자인 (3일차)

- [ ] 색, 글꼴, 간격, 카드 컴포넌트
- [ ] 수요 신호(많음, 보통, 적음) 색, 이유 태그 칩, 우선순위 표시, 네 가지 일 아이콘
- [ ] 3P 문구 자리: 달력은 파악하기, 알림 묶음은 계획하기, 카드 실행은 홍보하기
- [ ] 모바일 폭 375px 기준 네 화면 시안

완료 기준: 3일차 끝 팀 리뷰를 통과한다.

### F3 이번 주 달력 (4\~5일차)

받는 것: `GET /calendar`, `GET /sales?grain=weekday_daypart`(고정 샘플)

- [ ] 7일과 시간대 세 개의 칸에 수요 신호 색과 이유 태그
- [ ] 칸을 누르면 기준선, 예상 매출, 이유 한 줄
- [ ] 평소에는 열지 않는 화면이다. 오늘의 카드와 월요일 예고에서 들어오는 길을 둔다.

완료 기준: 고정 샘플에서 11/19 저녁과 야간, 11/21\~22 축제 시간이 많음으로 보이고, 11/18부터 계절 태그가 붙는다.

### F4 오늘의 카드와 설정 (5\~6일차)

받는 것: `GET /today`, `GET /plan`, `GET /reviews`, `PATCH /settings`, `POST /recompute`

- [ ] 알림 가능 시간별 묶음을 우선순위 순서로 보여준다. 승인 요청, 실행 알림, 예고, 매출 이상은 서로 다르게 보인다.
- [ ] 카드에는 일 종류, 승인 요청 시각, 실행 시각, 이유 한 줄. ①은 시점 분류도 함께 보인다.
- [ ] 같은 실행 시각의 기본 답변은 카드 한 장으로 묶는다.
- [ ] 초안 자리와 승인 수정 보류 버튼은 모양만 둔다(2차에서 동작).
- [ ] 설정: 알림 가능 시간 세 개와 점심, 저녁 장사 시간대. 저장하면 재계산한다.

완료 기준: 11/17 14:00 묶음이 기대 결과의 네 장 순서대로 보인다.

### F5 시뮬레이터 (6일차, 개발용)

받는 것: `GET /notifications`, `GET /reviews`, `POST /reviews`, `POST /dev/reset`

- [ ] 가상 시각 고르기. 모든 화면이 이 시각을 `now`로 쓴다.
- [ ] 한 주 알림 타임라인
- [ ] 리뷰 추가. 불만 리뷰를 넣으면 다음 알림 가능 시간에 빠른 응대가 나오는지 본다.
- [ ] 리뷰 분류 결과 목록과 초기화 버튼

완료 기준: 공통 탭의 데모 주간 기대 결과를 화면으로 재현한다.

### F6 실제 API 연결 (7일차)

받는 것: S3의 API v1

- [ ] 환경 변수 하나로 고정 샘플과 실제 API를 바꾼다.
- [ ] 로딩, 빈 상태, 오류 상태

완료 기준: 고정 샘플과 실제 API에서 같은 화면이 나온다.

### T1\~T3 (8\~10일차, 모두)

- [ ] T1: 화면에서 나온 문제를 작업 번호와 함께 그 줄의 담당에게 넘긴다.
- [ ] T2: 데모 주간 기대 결과를 시뮬레이터로 하나씩 대조한다.
- [ ] T3: 2차 화면 설계. 승인 수정 보류, 실행 도우미, 결과 리포트, 업로드, 매장 정보

## 확인할 것

- [ ] **답글 알림 동작** (3일차까지): 사장님이 답글을 달면 리뷰를 쓴 손님에게 알림이 가는지 네이버, 배민, 요기요, 쿠팡이츠별로 확인한다. ①의 핵심 가정이다.
- [ ] **알림톡 템플릿 규칙** (3일차까지): 버튼 링크, 변수 문구, 사전 심사 기간을 확인해 알림 문구에 반영한다. 발송은 2차다.
- [ ] **스마트플레이스 바로가기** (5일차까지): 리뷰 관리 화면과 메뉴 화면으로 바로 여는 링크가 모바일에서 되는지 확인한다. 안 되면 화면 위치를 안내한다.
