# 앱 · 서버 · DB · 분석은 어떻게 이어져 있나

도나(DONNA) 프로젝트를 처음 보는 사람이 **네 파트가 어떻게 연결되어 움직이는지** 이해하도록 쓴 문서입니다.
서버와 앱을 켜는 법은 [README.md](../README.md) 2장에 있습니다.

> 기준: 2026-11-12

---

## 1. 한 장으로 보기

### 식당에 비유하면

| 파트 | 비유 | 하는 일 | 담당 | 폴더 |
|---|---|---|---|---|
| **DB** | 장부 | 가게에서 일어난 일을 모두 적어 둔다 (주문, 리뷰, 알바 근무, 행사, 경기, 날씨) | 지호 | `server/db/` |
| **분석** | 장부를 읽는 분석가 | 장부를 읽고 정리한다 ("평소 매출은 얼마", "토요일은 바쁠 것", "이 손님은 단골", "이 리뷰는 불만") | 태성 | `server/app/analysis/` |
| **서버** | 가운데에서 일을 나르는 비서 | 장부를 꺼내 분석가에게 주고, 결과로 "언제 사장님께 무엇을 알릴지" 정하고, 앱에 보낸다 | 여헌 | `server/app/` (분석 제외) |
| **앱** | 사장님 휴대폰 화면 | 서버가 보낸 것을 보여 주고, 사장님이 누른 것을 서버에 보낸다 | 영웅 | `mobile/` |

### 데이터가 흐르는 길

```
                         ┌───────────────────────────── 서버 (server/app/) ─────────────────────────────┐
                         │                                                                               │
 ┌─────────┐  ① 요청     │  화면용 API          ② 가게 데이터 꺼내기    ③ 모양 맞추기      ④ 분석         │
 │   앱    │ ──────────▶ │  (modules/)  ──▶  (data_pipeline/  ──▶  (data_pipeline/ ──▶ (analysis/)       │
 │ mobile/ │             │       ▲            read_store_db)         db_rows_to_...)        │  태성        │
 │  영웅   │ ◀────────── │       │                  │                                       ▼              │
 └─────────┘  ⑧ 응답     │       │                  ▼                                ⑤ 계획 엔진          │
                         │       │            ┌───────────┐                           (planner/)          │
                         │       │            │    DB     │                                │              │
                         │       │            │ server/db/│                                ▼              │
                         │       │            │   지호     │                       ⑥ CLOVA X 글쓰기       │
                         │       │            └───────────┘                  (review_reply_writer/,       │
                         │       │                                            sentence_polish/)          │
                         │       └──────────── ⑦ 결과 보관함 (data_pipeline/store_snapshot_cache) ◀──────┘
                         └───────────────────────────────────────────────────────────────────────────────┘
```

| 단계 | 무슨 일 | 코드 |
|---|---|---|
| ① | 사장님이 앱 화면을 열면 앱이 서버에 데이터를 요청 | `mobile/src/lib/api.ts` |
| ② | 서버가 DB에서 **한 가게의, 지금 시각까지의** 데이터를 꺼냄 | `server/app/data_pipeline/read_store_db.py` |
| ③ | DB 모양을 분석이 읽는 모양으로 번역 | `server/app/data_pipeline/db_rows_to_analysis_inputs.py` |
| ④ | 분석: 하루 매출, 35일 달력 예측, 단골 판정, 리뷰 분류, 반복 불만 | `server/app/analysis/` |
| ⑤ | 계획 엔진: 할 일마다 언제 사장님께 승인을 받고 언제 실행할지 | `server/app/planner/` |
| ⑥ | CLOVA X: 리뷰 답글 초안을 쓰고, 화면 문장을 사장님이 읽기 편하게 다듬음 | `server/app/review_reply_writer/`, `server/app/sentence_polish/` |
| ⑦ | 계산 결과를 가게별로 보관 (10분마다 다시 계산) | `server/app/data_pipeline/store_snapshot_cache.py` |
| ⑧ | 화면에 맞는 모양으로 골라서 앱에 응답 | `server/app/modules/` |

**중요한 규칙 세 가지**
1. **DB에 들어가는 문은 하나**: 서버에서 DB를 읽는 곳은 `read_store_db.py`뿐입니다. 나중에 로그인한 사장님이 자기 가게만 보게 막는 보안 처리도 이 한 곳에 넣으면 됩니다.
2. **앱은 DB와 분석을 직접 모른다**: 앱은 서버 주소(`/api/...`)만 압니다. DB나 분석 코드가 바뀌어도 서버 응답 모양만 같으면 앱은 고칠 필요가 없습니다.
3. **진짜 현재 시각**: 가짜 시각을 쓰지 않습니다. 목업 DB에는 12/31까지 주문이 미리 들어 있지만, 서버는 지금 시각 이전 데이터만 꺼냅니다. 날짜가 지나면 그날 데이터가 하나씩 보이기 시작합니다.

## 2. 파트별 자세히

### 2-1. DB (지호, `server/db/`)

가상 가게 3곳의 2026년 1년치 장사 기록입니다. 별도 프로그램 없이 **파일 하나가 DB**인 SQLite를 씁니다.

```
server/db/data/common.db   모든 가게가 같이 쓰는 표: events(행사), games(경기), weather_daily(날씨)
server/db/data/s001.db     s001 한림국수 전용 표
server/db/data/s002.db     s002 두리맥주 전용 표
server/db/data/s003.db     s003 석사돈가스 전용 표
```

| 가게 전용 표 | 한 줄이 뜻하는 것 | 주요 칸 |
|---|---|---|
| `store` | 가게 정보 | 이름, 업종, 위치, 영업시간, 쉬는 요일, 알림 시각 |
| `menu` | 메뉴 | 이름, 분류, 가격 |
| `orders` | 주문 한 건 | 주문 시각, 홀/배달, 손님 키, 금액 |
| `order_items` | 주문 속 메뉴 | 메뉴, 수량, 단가 |
| `reviews` | 리뷰 | 쓴 시각, 별점, 글, 이어진 주문 |
| `staff` | 알바 | 이름, 시급 |
| `shifts` | 근무 한 번 | 출근, 퇴근 시각 |

| 가게 | 장사 시간 | 알바 |
|---|---|---|
| s001 한림국수 | 10:00 ~ 22:00, 쉬는 날 없음 | 5명 |
| s002 두리맥주 | 17:00 ~ 다음 날 03:00 | 5명 |
| s003 석사돈가스 | 11:00 ~ 21:00, 월요일 휴무 | 5명 |

- 데이터는 `server/db/mock/generate.py`가 만듭니다. 같은 시드면 항상 같은 데이터가 나옵니다.
- 리뷰는 11/10까지만 있습니다. 데모 주간(11/16~22)의 행사, 단골, 불만 리뷰는 아직 넣지 않았습니다.

### 2-2. 분석 (태성, `server/app/analysis/`)

**넣는 것**: `AnalysisInputs` 하나에 가게 정보, 주문, 주문 메뉴, 메뉴, 근무, 행사, 경기, 날씨, 리뷰를 담아 넣고, **지금 시각(`now`)**을 함께 줍니다. 분석은 `now` 이후 데이터는 보지 않습니다.

**나오는 것** (6가지):

| 결과 | 분석가가 하는 말 | 계산 방법 | 쓰는 곳 |
|---|---|---|---|
| `sales_daily` 하루 매출 | "11/10 점심에 35만 원, 알바비 빼면 28만 원" | 주문을 날짜 × 시간대로 더함 | 매출 탭 |
| `calendar_day` 35일 달력 | "11/26 저녁은 비 때문에 평소보다 18% 바쁠 것" | 지난 8주 같은 요일 매출(평소) × 예전 비슷한 날(축제·경기·비)의 차이 | 이번 주 화면, 메뉴판, 포스터 |
| `customer_cycle` 단골 판정 | "이 손님은 한 달에 한 번 오는 단골" | 최근 4번 방문 간격 (일주일쯤: 매주, 한 달쯤: 매달) | 답글 말투, 재주문 인사 |
| `review_label` 리뷰 분류 | "배달이 늦었다는 불만, 빨리 답해야 함" | 키워드 규칙 (HyperCLOVA X 분류도 있지만 지금은 끔) | 답글 순서와 말투 |
| `risk_signal` 반복 불만 | "7일 안에 배달 지연 불만이 3건" | 같은 불만 종류를 셈 | 점검 카드 |
| `sales_anomaly` 매출 이상 | "어제 점심 매출이 너무 적었음" | **아직 코드 없음** | 매출 이상 알림 |

### 2-3. 서버 (여헌, `server/app/`)

서버는 세 가지 일을 합니다.

**① DB와 분석을 잇기** (`data_pipeline/`)

DB와 분석은 같은 내용을 다르게 적습니다. 서버가 내용은 그대로 두고 **표현만** 맞춥니다.

| DB에 적힌 것 | 분석이 읽는 것 | 비고 |
|---|---|---|
| 리뷰 번호 `1` | `rv_001` | 행사 `event_001`, 경기 `game_001`, 알바 `staff_001` |
| `hall`, `delivery`, `main` | `HALL`, `DELIVERY`, `MAIN` | 소문자 → 대문자 |
| `content`, `starts_at`, `precip_mm` | `text`, `start_at`, `rain_mm` | 칸 이름만 다름 |
| 알바 이름 | 넘기지 않음 | 인건비 계산에는 시간과 시급만 필요. 이름은 알바 API로 앱에 따로 보냄 |
| (칸 없음) 리뷰가 달린 곳 | 배달 주문과 이어진 리뷰 → 배민, 나머지 → 네이버 | **임시 규칙** |
| 행사 거리(숫자 하나) | 가게 위치와 행사 위치로 가게마다 다시 계산 | 가게마다 행사까지 거리가 달라서 |
| (분석 기본) 아침/점심/저녁 | **점심(~15시) / 저녁(15~20시) / 밤(20시~)** | 앱과 계획 엔진이 이 기준을 씀 |

**② 할 일과 알림 시각 정하기** (`planner/`, 계획 엔진)

분석 결과를 받아 사장님이 할 일과, 그 일을 **언제 승인받고 언제 실행할지** 정합니다. AI가 아니라 날짜·시간 규칙으로 계산합니다. 알림은 하루 세 번(출근 후, 오후, 마감 전)으로 모아서 보냅니다.

| 할 일 | 언제 생기나 | 승인 요청 | 실행 |
|---|---|---|---|
| 불만 리뷰 답글 | 불만 리뷰가 달리면 | 리뷰 뒤 첫 알림 시각 | 승인과 동시에 |
| 그 밖의 리뷰 답글 | 지난 토요일 11:00 ~ 이번 토요일 11:00에 달린 리뷰 | 이번 토요일 10:00에 모아서 | 토요일 11:00 |
| 매달 단골 재주문 인사 | 매달 단골이 리뷰를 남기면 | 답글 4주 뒤 토요일 10:00 | 같은 날 11:00 |
| 메뉴판 순서 바꾸기 | 달력 이유(계절, 행사, 경기)가 바뀌는 날 | 전날 오후 | 당일 출근 후 |
| 행사·경기 포스터 | 많이 바쁠 행사·경기 | 3일 전 오후 | 2일 전 출근 후 |
| 반복 불만 점검 | 반복 불만 신호가 열리면 | 발견 뒤 첫 오후 | 없음 |

화면에는 리뷰 답글 중 **이번 한 주 몫만** 보입니다. 토요일 11시가 지나면 새 한 주가 시작됩니다.

**③ CLOVA X로 글쓰기**

| 무엇 | 폴더 | 프롬프트 (말투를 바꾸려면 여기만) |
|---|---|---|
| 리뷰 답글 초안 | `review_reply_writer/` | `prompts/review_reply_prompt.txt` |
| 매달 단골 재주문 인사 | `review_reply_writer/` | `prompts/reorder_nudge_prompt.txt` |
| 답글 다시 쓰기 (더 짧게 / 더 정중하게) | `review_reply_writer/` | `prompts/rewrite_reply_prompt.txt` |
| 달력 이유 한 줄 다듬기 | `sentence_polish/` | `prompts/calendar_reason_prompt.txt` |
| 할 일 카드 문구 다듬기 | `sentence_polish/` | `prompts/plan_card_prompt.txt` |
| 월요일 미리보기, 매출 이상 알림 다듬기 | `sentence_polish/` | `prompts/notice_prompt.txt` |

- **답글 초안**: 리뷰 글, 별점, 불만 종류(분석), 단골 여부(분석)를 읽고 사장님이 쓴 것 같은 답글을 씁니다. 재주문 인사는 손님의 지난 리뷰를 보내지 않고 "늘 찾아 주셔서 감사해요 + 계절 메뉴 추천"으로 씁니다.
- **문장 다듬기**: 분석과 계획 엔진이 정해진 틀로 만든 딱딱한 문장을 자연스럽게 바꿉니다. (예: "겨울 영향으로 평소보다 5% 많을 것 같아요" → "날이 추워져서 평소보다 5% 정도 주문이 늘 것 같아요")
- **안전장치**: 숫자나 행사 이름이 바뀐 문장, 보상 약속(환불, 무료 등), 지어낸 가게 사정(국내산 등), 손님을 기억하는 척하는 말(지난 방문 때 등)은 버리고 원래 문장이나 앱 기본 문장을 씁니다.
- **CLOVA 키가 없어도** 앱은 원래 문장과 기본 답글로 정상 동작합니다.

### 2-4. 앱 (영웅, `mobile/`)

Expo(React Native)로 만든 앱입니다. 한 코드로 웹, iOS, 안드로이드가 됩니다. 개발할 때는 웹(`http://localhost:8082`)으로 봅니다.

- **데이터 읽기**는 `mobile/src/lib/api.ts` 한 곳에서만 합니다.
- **`mobile/.env.local`의 스위치 하나**로 데이터 출처가 바뀝니다.
  - `EXPO_PUBLIC_USE_MOCK=false`: 우리 서버에서 실제 데이터를 받음 (지금 설정)
  - `true` 또는 줄이 없음: 앱 안의 예시 데이터(데모 주간 이야기)로 동작. 서버가 필요 없음
- **사장님 동작**(답글 올리기, 메뉴 순서 바꾸기, 포스터 만들기)은 `mobile/src/lib/actions.ts`에 있습니다. "다시 쓰기"만 서버에 연결됐고, 나머지는 아직 흉내만 냅니다.
- **이 기기 저장소**: 가입, 처음 쓰는 날, 끝낸 카드는 브라우저 저장소에 저장됩니다. 서버를 다시 켜면 앱도 처음 상태로 돌아갑니다 (5장).

## 3. 화면별로 따라가 보기

### 예 1) 홈 화면을 열면

1. 앱이 서버에 `today`, `plan`, `reviews`, `calendar`, `settings` 5개를 한꺼번에 요청합니다.
2. 서버는 보관함에 s001 결과가 있는지 봅니다. 없거나 10분이 지났으면 다시 계산합니다.
   - DB에서 s001의 지금까지 데이터를 꺼냄 → 번역 → 분석 6가지 → 계획 엔진 → 이번 한 주 답글만 남김 → CLOVA로 답글 초안 쓰기
   - 처음 계산은 분석과 초안 쓰기 때문에 **8초쯤** 걸립니다. 그 뒤 10분 동안은 바로 응답합니다.
3. `today`는 오늘 알림 시각별로 할 일 id만 묶어서 보냅니다. 카드 내용(이유 한 줄, 답글 초안)은 `plan`에서 같은 id를 찾아 씁니다.
4. 앱이 카드를 그립니다. 답글 카드에는 서버가 보낸 `draft_text`(CLOVA 초안)가 보입니다.

### 예 2) "이번 주 손님" 화면의 "바쁨"

1. 앱이 `GET /api/calendar`를 요청합니다.
2. 서버는 분석의 35일 달력을 보냅니다. 칸마다 평소 매출, 예상 매출, 신호(`HIGH` / `NORMAL` / `LOW`), 이유, 다듬은 이유 문장이 들어 있습니다.
3. 앱은 하루 중 `HIGH` 칸이 하나라도 있으면 "바쁨"을 붙입니다. (예상이 평소보다 15% 넘게 많으면 `HIGH`)

### 예 3) 답글을 "더 정중하게" 고치기

1. 앱이 `POST /api/replies/rewrite`에 지금 답글, `style: "polite"`, 할 일 id를 보냅니다.
2. 서버가 그 할 일의 근거 리뷰를 찾아, 답글과 함께 CLOVA X에 보냅니다.
3. 다시 쓴 답글이 안전 검사를 통과하면 앱에 돌려줍니다. 실패하면 오류를 보내고, 앱은 "다시 하기"를 보여 줍니다.

### 예 4) 매출 탭

| 화면 | 데이터가 오는 길 |
|---|---|
| 이번 주와 지난주, 시간대와 요일, 달별 | DB → 분석(하루 매출, 달력 예상) → 서버. 오늘 지금까지 매출만 DB에서 바로 |
| 오늘 실시간, 메뉴별, 홀/배달 | DB → 서버 (분석에 시간별·메뉴별 매출이 없어서). 단골 여부만 분석 결과 사용 |

## 5. 알아 두면 좋은 동작

**계산 결과 보관**
- 분석은 가게 하나에 2~3초, 답글 초안까지 처음에는 8초쯤 걸립니다. 그래서 결과를 가게별로 보관하고 **10분마다** 다시 계산합니다.
- 간격은 서버 `.env`의 `SNAPSHOT_REFRESH_MINUTES`로 바꿉니다.
- 사장님이 설정을 고치면 그 가게 결과를 지우고 바로 다시 계산합니다.

**서버를 다시 켜면 앱도 처음부터**
- 서버는 켜질 때마다 새 번호(`boot_id`)를 정합니다.
- 앱은 켜질 때 그 번호가 지난번과 다르면 브라우저에 저장된 값(가입, 끝낸 카드 등)을 모두 지웁니다. (`mobile/src/lib/storage.ts`)
- 같은 서버가 켜져 있는 동안에는 새로 고침해도 지우지 않습니다.
- 서버 코드를 고쳐서 `--reload`로 자동으로 다시 켜질 때도 초기화됩니다.

**가게 고르기**
- 로그인이 아직 없어서 서버 `.env`의 `DEMO_STORE_ID`로 정합니다. (`server/app/data_pipeline/store_selection.py`)
- 로그인이 생기면 이 파일에서 "로그인한 사장님의 가게"로 바꾸고 다른 가게는 막습니다.
